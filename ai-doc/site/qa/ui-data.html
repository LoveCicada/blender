Q101–150 · UI–数据

两条链，同一份数据

面板、快捷键、Python 都不是第二份场景拷贝。磁盘是 DNA，对外名字是 RNA，一次动作是 Operator，尾巴是标脏 + 通知。函数走读见数据章。

DNA 与 SDNA

101 按钮为什么不直接写 mesh->remesh_voxel_size？

控件拿的是 RNA 属性。RNA 按 SDNA offset 或 get/set 写 C 字段。这样 UI 不依赖头文件布局，旧文件也能对上改名成员。

直接赋值会跳过 update、撤销和消息总线。

RNA_property_float_set · DNA

102 SDNA 表什么时候生成、存在哪？

构建期 makesdna/intern/makesdna.cc 扫 DNA_*_types.h 得到 DNAstr。运行时 DNA_sdna_current_get() 解码当前布局。每个 .blend 再写一份当时的 DNA1。

打开旧文件时拿文件里的表和当前表比。

dna_genfile.cc · makesdna

103 打开旧版本文件字段对不上怎么办？

BLO_read_from_file → read_file_dna → DNA_struct_get_compareflags。没变就 memcpy；变了就 DNA_struct_reconstruct。改名靠 dna_rename_defs.h。

这就是「可版本对齐的结构体数据库」，不是场景树迁移。

DNA_struct_reconstruct · 读文件

104 ID 名字前两字节类型码有什么用？

如 ID_ME 标这块是 Mesh。链表、查找、用户计数、depsgraph 节点都按 ID 类型走。RNA 的 "Mesh" 继承 "ID"，和这个码对应。

改显示名不会改类型码。

DNA_ID.h · Mesh 从 ID 开始

105 ID.recalc 是给谁看的？

给 depsgraph / 更新系统看「这块脏了哪类」（几何、变换、着色、参数）。DEG_id_tag_update 写这类标志。UI 不读它来画按钮。

撤销也可能与 recalc 交互，细节不在本问答展开。

ID.recalc · 标脏

106 MeshRuntime 为什么「明确不存盘」？

运行时缓存：编辑态 BMesh、求值包装、绘制用加速结构。存盘只保可版本化的数组与属性。换版本或换实现不必迁移这些指针。

看见 runtime 就不要在 RNA 里当用户属性暴露成文件字段。

MeshRuntime *runtime · 不进文件

107 CustomData 进文件吗？

进。UV、顶点色等层跟 Mesh 一起序列化。编辑模式转换必须带着走，否则 Tab 一圈属性丢了。

它不是 RNA 的「动态 dict」，仍是 C 布局 + 层描述。

vert_data / edge_data / ... · DNA

108 为什么说 DNA 不是 API？

Python 和面板禁止依赖「结构体第几个 int」。API 是 RNA 标识符。DNA 可以加字段、改顺序（靠 SDNA），只要 RNA 绑定还在。

插件读 mesh.remesh_voxel_size，不读某个 offset。

makesrna

109 AnimData *adt 为什么挂在 Mesh 上？

数据块可以自己有动画/驱动。求值读 adt，不是 UI 每帧写字段。没有 adt 的块就没有这块曲线。

功能上「网格参数也能插帧」，数据上仍是 ID 附属指针。

AnimData *adt · makesdna

110 新建 Mesh 时谁填充默认 DNA？

blenkernel 的创建函数分配 ID、填默认标志和空几何。makesdna 只描述形状，不「new 一个立方体」。立方体图元是 editors/object 或 BKE 原语。

UI 的 Add Cube 是 Operator，不是 DNA 默认值。

BKE_mesh_* · blenkernel

RNA 命名与 update

111 PointerRNA / StructRNA / PropertyRNA 各是什么？

PointerRNA：指向哪块数据、属于哪个 owner_id、什么 type。StructRNA：类型（"Mesh" 继承 "ID"）。PropertyRNA：一个属性的标识符、类型、sdna 或回调、update、noteflag。

UI 拿到的永远是 Pointer + Property，不是裸 Mesh *。

RNA_types.hh · 三个类型

112 RNA_def_property_float_sdna 做了什么？

把属性绑到结构体成员名，生成代码后变成 offset 访问。定义阶段写的是成员字符串，不是运行时手算字节。

布尔还可以绑 flag 位：RNA_def_property_boolean_sdna(..., "texspace_flag", ME_TEXSPACE_FLAG_AUTO)。

rna_mesh.cc · 绑到 DNA

113 为什么有的属性不用 sdna 而用 get/set？

换指针要改用户计数、校验类型、处理空值。Object.data 用 rna_Object_data_get/set。计算属性、枚举映射也走函数。

看见 funcs 不要以为没存盘；可能 DNA 在别处，或根本是派生值。

rna_object.cc · RNA

114 RNA_def_property_update 的字符串何时变成函数指针？

定义时先存 "rna_Mesh_update_draw" 这类名字，makesrna 生成后再补成指针。运行时 RNA_property_update 调 prop->update。

不要在头文件里找这个字符串当公开 API。

makesrna.cc PROCESS_ITEMS · 定义

115 rna_Mesh_update_geom_and_params 和 update_draw 差在哪？

前者 DEG_id_tag_update(..., ID_RECALC_GEOMETRY | ID_RECALC_PARAMETERS) 并 notifier。后者常常只 WM_main_add_notifier，给「只影响显示」的属性。体素尺寸等还可 PROP_NO_DEG_UPDATE，等 Remesh 按钮再算。

选错 update 会出现「滑条动了但网格不重建」或「不该重建却重建」。

rna_mesh.cc · 写完为什么要 update

116 PROP_NO_DEG_UPDATE 是什么设计？

允许写 DNA 却不立刻标 depsgraph。贵操作（重网格）等用户确认。UI 仍刷新控件（消息总线）。

不是「这个属性不更新」，是「不自动求值」。

PROP_NO_DEG_UPDATE · RNA

117 RNA_property_update 默认还会做什么？

调自定义 update 后，默认再 DEG_id_tag_update（可关），并 WM_msg_publish_rna 刷新绑定该属性的按钮。

同一属性出现在多个面板时，靠消息总线对齐显示，不必每个面板自己轮询。

rna_access.cc · RNA

118 bpy.types.Mesh 是 Python 自己的类吗？

是 StructRNA 的包装（bpy_rna.cc）。赋值走 RNA_property_*_set，成功后 pyrna_py_to_prop 调 RNA_property_update。不是普通 __dict__。

context.mesh.remesh_voxel_size = 0.1 因此能写到 C 结构体。

source/blender/python/intern/bpy_rna.cc · Python 怎么碰到 RNA

119 bpy.ops 和属性赋值是一条链吗？

不是。bpy.ops.mesh.subdivide() 走 bpy_operator_function.cc → WM_operator_call_py，即链 B。属性赋值是链 A。

两条尾巴都可能 tag + notifier，但只有 Operator 默认按 flag 推撤销。

WM_operator_call_py · 两条链

120 Operator 自己的 RNA 属性存在哪？

注册时 RNA_def_int(ot->srna, "number_cuts", ...) 挂在 wmOperatorType 的 StructRNA 上，不是 Mesh DNA。调用时参数在 wmOperator 实例里。

重做（Redo 面板）改的是这些属性再 exec 一次，不是改 Mesh 的 DNA 字段名。

MESH_OT_subdivide · 注册

121 RNA 枚举和 C 枚举必须同名吗？

不必。RNA 给 UI 标识符和翻译项；C 用自己的 enum。定义时做映射。改 UI 标签不改文件里的 int，只要 item value 稳定。

这是「对外名字」层存在的原因之一。

RNA_def_property_enum_* · makesrna

122 只读 RNA 属性还会触发 update 吗？

UI 不能 set。派生 getter 若被 Python 赋值会失败。update 发生在成功写入之后。只读用来暴露计算值（顶点数等），避免用户当可存盘字段改。

PROP_EDITABLE · RNA

Python UI

123 layout.prop 在 C 里是什么？

rna_ui_api.cc → rna_uiItemR：根据 PointerRNA + 属性标识符创建控件，绑定到那份 DNA。Python 只传 mesh, "use_auto_texspace"。

draw 函数每次重画可以重建布局，状态在 RNA，不在 Panel 实例。

rna_uiItemR · 面板只画

124 layout.operator 会立刻 exec 吗？

不会。它只把 Operator 名画成按钮（rna_uiItemO）。按下才 WM_operator_name_call_*。菜单也一样。

所以 bl_ui 里搜不到 BM_mesh_esubdivide。

rna_uiItemO · Python UI

125 Panel.poll 失败时数据还在吗？

在。poll 只决定这张面板画不画。Mesh ID 仍在 Main。换到无网格物体，context.mesh 空，DATA_PT_* 隐藏。

不要用 poll 当删除数据。

MeshButtonsPanel.poll · Mesh 属性面板

126 bl_context = "data" 是怎么对上的？

属性编辑器按上下文页（物体、数据、材质…）过滤面板。buttons 空间设置当前 context 字符串，与 bl_context 匹配。再由 buttons_context() 填 mesh 等指针。

这是 UI 空间协议，不是 RNA 类型系统的一部分。

properties_data_mesh.py · Python UI

127 拖动滑条时谁调用 button_value_set？

界面事件在 interface.cc：button_value_set → RNA_property_float_set。松手/确认路径上 interface_handlers.cc 调 RNA_property_update。这是链 A 的中段。

WM 循环包在外面：wm_window_events_process → handlers。

button_value_set · 链 A

128 Python 写的 Operator 和 C 的 MESH_OT_* 一张表吗？

是。同一套 wmOperatorType 表。bl_operators/mesh.py 用 bl_idname + execute 注册。调用路径仍是 WM。编辑模式主力仍是 C。

idname 冲突会覆盖，这是扩展点也是风险。

scripts/startup/bl_operators/ · Python 里也有 Operator

129 为什么重做面板能改 number_cuts？

上次 Operator 的 RNA 属性还在。改参数再 exec，不经过 bl_ui 里手写循环。Register 标志（OPTYPE_REGISTER）让这次调用出现在重做栈。

和 Mesh DNA 上的字段不是同一个 PropertyRNA。

OPTYPE_REGISTER · MESH_OT_subdivide

130 菜单里的 layout.menu 会嵌套执行吗？

layout.menu("VIEW3D_MT_view") 只引用另一份 Menu 的 draw。真正命令仍是里面的 operator/prop。头栏 VIEW3D_MT_editor_menus 是组装，不是逻辑层。

space_view3d.py · View3D 菜单

131 翻译和 RNA 什么关系？

RNA 有 name / description 供界面和工具提示。locale 目录本站不拉。分析设计时把标识符当稳定 API，把显示字符串当翻译层。

改翻译不会改 .blend 字段。

makesrna

132 插件面板遵循同一条 UI–数据链吗？

是。自定义 Panel 仍 layout.prop / operator。自定义 Property 要挂到 RNA（ID properties 或注册 PropertyGroup）。不要在 draw 里改顶点数组。

这是官方扩展模型，不是本站范围外的另一套。

bpy.types.Panel · Python UI

Operator 与 WM

133 WM_main 一圈四步是什么？

处理窗口事件、跑 handlers（含 Operator）、消化 notifiers、绘制。进循环前常 wm_event_do_refresh_wm_and_depsgraph，避免未求值就跑命令或画。

视口不轮询每个顶点，靠这一圈的脏标记。

windowmanager/intern/wm.cc · WM 循环

134 MESH_OT_* 在哪里挂进表？

WM_operatortype_append 创建类型并调用填充函数。spacetypes.cc → ED_operatortypes_mesh()（mesh_ops.cc）挂一串网格命令。

idname MESH_OT_subdivide 对应 bpy.ops.mesh.subdivide。

wm_operator_type.cc · 注册

135 poll 失败为什么像「快捷键坏了」？

ED_operator_editmesh 要求 CTX_data_edit_object 是带 BMEditMesh 的网格。物体模式静默失败。这是上下文门，不是 keymap 没绑上。

调试功能先看 poll，再看 exec。

editors/screen/screen_ops.cc · poll

136 invoke / exec / modal 怎么选？

wm_operator_invoke：先 poll；有 event 且有 invoke 则走 invoke（可进 modal）；否则 exec。结束且 OPERATOR_FINISHED → wm_operator_finished。

G/R/S 是 modal；细分通常 exec 一次做完。

wm_operator_invoke · 调用路径

137 bContext 为什么要存在？

签名固定 (bContext *C, wmOperator *op)，从 window / screen / area / region 和命名指针取「当前网格」。避免全局 G.editmesh。

同一 exec 在脚本里靠覆盖 context 工作。

blenkernel/intern/context.cc · bContext

138 快捷键路径和按钮路径在哪汇合？

keymap：wm_event_do_handlers → wm_eventmatch → wm_handler_operator_call。按钮：WM_operator_name_call → wm_operator_call_internal。之后都是 invoke/exec。

汇合点在 WM，不在 editors/mesh。

windowmanager

139 为什么 Operator 要读上下文而不能读全局当前物体？

多窗口、多场景、后台脚本可以没有「当前 3D 视图」。上下文显式失败（poll）比隐式用错物体安全。

这是 UI–数据链能被 Python 复用的前提。

CTX_data_view_layer · Operator

140 EDBM_update 在链 B 里扮演什么？

编辑工具改完 BMesh 后的标准收尾：重算法线/looptris，DEG_id_tag_update(&mesh->id, ID_RECALC_GEOMETRY)，WM_main_add_notifier(NC_GEOM | ND_DATA, ...)。修改器应用不在这里。

物体模式工具走别的 tag，没有这一跳。

editmesh_utils.cc · 链 B

141 notifier 的 NC_GEOM | ND_DATA 是给谁的？

入队 WM_main_add_notifier / WM_event_add_notifier。出队 wm_event_do_notifiers，各编辑器 listener 决定重画哪块区域。它不携带顶点缓冲。

RNA 无 context 时常用 WM_main_add_notifier。

Notifier 与撤销

142 宏 Operator（挤出+移动）怎样保持一条撤销？

执行期间 wm->op_undo_depth 增加，嵌套 op 不再各推一步。外层 finished 才 ED_undo_push_op。用户觉得是一次挤出。

没有这个深度，G 会单独成一步撤销。

wm->op_undo_depth · 撤销

标脏与撤销

143 DEG_id_tag_update 之后谁真正求值？

不是同步在 tag 里算完修改器。WM 稍后 BKE_scene_graph_update_tagged → DEG_evaluate_on_refresh。UI 链停在「图脏了」。

像素是下一层的事，见渲染问答。

DEG_evaluate_on_refresh · UI–数据地图

144 为什么视口不轮询每个顶点？

那样每帧扫全部 Mesh。设计是：写数据的人负责 tag + notifier；绘制的人假定求值世界已更新。这是性能与模块解耦。

漏 tag 的典型症状：数据改了画面不动。

改完如何让别人知道

145 OPTYPE_UNDO 什么时候推栈？

wm_operator_finished → ED_undo_push_op（editors/undo/ed_undo.cc）。flag 没有则不推。拖属性的链 A 走属性撤销/记忆，和命令撤销不是同一句调用。

细分注册了 OPTYPE_REGISTER | OPTYPE_UNDO。

ED_undo_push_op · 撤销

146 为什么 bpy.ops 默认常常不进撤销？

脚本批量调用若每步都推栈会爆内存、也难用。默认压住，除非标明 is_undo。C 快捷键路径按类型 flag 推。

写插件时要意识到「我调了 ops 但 Ctrl+Z 回不去」可能是这个策略。

is_undo · Notifier 与撤销

147 链 A 拖滑条有撤销吗？

界面有属性撤销/拖动开始时的快照机制（具体按钮类型而异），不是 ED_undo_push_op 那条命令栈。分析时不要把两种撤销混成一个函数。

复杂工具用 Operator 才能进统一命令撤销。

两条链

148 编辑模式多一跳指什么？

Operator → 改 BMesh →（必要时写回 Mesh）→ tag。物体模式没有 BMesh。漏了 EDBM_update 就会出现「拓扑改了、depsgraph 不知道」。

接到建模 · 留在编辑模式

149 消息总线 WM_msg_publish_rna 和 notifier 重复吗？

粒度不同。消息总线对准「这个 RNA 属性变了，绑定它的控件刷新」。notifier 对准「这类数据变了，哪块编辑器要听」。两者常一起出现。

只发一个，可能滑条数字对了但 3D 视口不刷，或相反。

WM_msg_publish_rna · update

150 UI–数据章停在哪，为什么交给渲染章？

停在「数据变了、图脏了」。谁用 Viewport 图、谁用 Render 图、谁出光栅、谁出路径追踪，是求值之后的分道。UI 链不应直接调 Cycles kernel。
