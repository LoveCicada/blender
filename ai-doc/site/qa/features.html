物体模式 / 变换 / Tab

051 物体模式移动立方体，会进 BMesh 吗？

不会。G 走 transform modal，写回 Object 的位置/旋转/缩放。网格数组不动。depsgraph 标 TRANSFORM，视口重画物体矩阵。

只有进入编辑模式后，同一套 G 才写 BMesh 顶点。

editors/transform/ · transform · 按功能

052 Shift+A 添加网格走哪条功能链？

editors/object 创建 Object + Mesh ID，链进 Main 和集合。新 Mesh 是数组网格，默认物体模式。不先建 BMesh。

随后若立刻 Tab，再 EDBM_mesh_make 转半边。

editors/object/ · editors/object

053 Tab 进编辑模式用户感觉「没变」，源码做了什么？

OBJECT_OT_editmode_toggle：ob->mode = OB_MODE_EDIT，EDBM_mesh_make → BM_mesh_bm_from_me，挂 edit_mesh，重算 looptris/法线，DEG_id_tag_update。屏幕上仍是同一物体，存储格式已经换了。

DNA 的 verts_num 可以暂时落后于 BMesh，直到 flush / 退出。

editmode_enter_ex · 进出编辑模式

054 Tab 出去时为什么可能「卡一下」？

离开要 EDBM_mesh_load_ex → BM_mesh_bm_to_me 把半边写回数组，再释放 edit_mesh。大网格是一次完整转换，不是只改模式标志。

求值中的 BM_mesh_bm_to_me_for_eval 是临时数组，不代表用户已退出。

editmode_exit_ex · 进出编辑模式

055 物体模式选中和高亮是谁画的？

选择状态在 View Layer / Object 标志上。轮廓和原点是 overlay，不是 Workbench 材质。换 Solid/Material 通常还在。

不要在 Cycles kernel 里找活动物体描边。

View3D · overlay

056 应用物体变换（Ctrl+A）改的是网格还是物体？

「应用位置/旋转/缩放」把矩阵烤进数据（网格物体则烤进顶点或把变换归单位）。这是 editors/object，物体模式功能。编辑模式里另有「把变换应用到顶点」的语义，仍不是修改器 Apply。

和「应用修改器」名字像，路径完全不同。

OBJECT_OT_transform_apply · editors/object

057 父子关系求值时发生什么？

DNA 存 parent 指针。视口看到的世界矩阵由 depsgraph 的 TRANSFORM 组件算出。改父物体，子物体不用用户再点一次「计算」。

编辑子物体网格仍改子 Mesh/BMesh，不自动改父网格。

depsgraph · blenkernel

058 集合与「是否可见」属于建模功能吗？

集合是组织与可见性（viewport / render hide）。depsgraph 建图和可见性阶段会读这些标志。它不改拓扑，但决定物体会不会进视口图或渲染图。

hide_viewport 与 hide_render 可以不一致：这就是两张求值图分叉的用户开关之一。

DAG_EVAL_VIEWPORT · 两种模式

059 复制物体（Shift+D）复制的是哪份数据？

默认常复制 Object，Mesh 可以是共享或新拷贝（用户计数）。共享时两个物体改同一 Mesh；编辑模式进的是那份 Mesh 的 edit_mesh。

功能上看「两个立方体」，数据上可能仍是一块 ID。

ID.us · blenkernel

060 为什么物体模式没有「挤出」？

挤出要半边拓扑。poll ED_operator_editmesh 失败则快捷键无效。用户必须先 Tab。这是功能门，不是键位丢了。

物体模式对应的是「复制物体」或修改器，不是面挤出。

ED_operator_editmesh · 挤出

061 原点（origin）移动是网格功能还是物体功能？

改的是物体与数据的相对原点，通常走 object 编辑器：平移数据或改物体矩阵，使视觉位置不变、原点变。不是 BMO。

编辑模式里也可以「设原点」，仍要写回 Mesh 坐标与物体位置配对。

editors/object

062 多物体同时编辑时功能链有何不同？

exec 用 BKE_view_layer_array_from_objects_in_edit_mode_unique_data 扫所有编辑态网格，对每份 unique Mesh 跑一遍。共享 data 的物体不会被算两次。

功能上「挤出两个立方体」，实现上按数据块去重。

BKE_editmesh_from_object · Operator

编辑模式改网格

063 点选一个顶点，改的是 DNA 吗？

选择标志在 BMesh 元素上。DNA 选择层要等 flush / 退出才对齐。needs_flush_to_id 表示磁盘布局过期。

视口编辑线来自 editmesh 的 looptris，不是读 verts_num 旧值。

BM_ELEM_SELECT · 两套网格

064 挤出（E）实际调用了什么？

菜单常见 MESH_OT_extrude_region_move：edbm_extrude_ex → BMO "extrude_face_region" → bmo_extrude_face_region_exec → EDBM_update，再接 transform modal 让你拖。

只挤出不移动是另一条 Operator。用户手感是一次动作，源码是命令组合。

editmesh_extrude.cc · 挤出与 BMO

065 为什么挤出时文件里的顶点数可以还是旧的？

留在编辑模式只改 em->bm。写回 DNA 发生在退出或显式 flush。这是功能承诺：连续工具不要每步序列化整网。

保存文件前会离开编辑或 flush，否则盘上仍应是一致数组网格。

EDBM_update · 建模

066 溶解顶点走 BMO 还是直接删数组？

"dissolve_verts" → bmo_dissolve_verts_exec → MESH_OT_dissolve_verts。半边溶解要重连面，不能只把顶点从数组 pop 掉。

poll 同样是 ED_operator_editmesh。

bmo_dissolve.cc · 溶解

067 细分（W / Ctrl+1 等）为什么有的不走 BMO 表？

MESH_OT_subdivide 的 exec 直接 BM_mesh_esubdivide。历史与性能：这条路径更早、更专用。挤出/溶解走统一表。功能上都是「编辑态改拓扑」。

不要要求每个工具都有 BMO 名。

edbm_subdivide_exec · MESH_OT_subdivide

068 刀切、环切功能落在哪？

仍是 editors/mesh + BMesh（多为 modal）。本问答不展开每个工具，但边界相同：改 bm，EDBM_update 标几何脏，不立刻算修改器。

环切预览是 modal 期间的临时几何，确认后才进 BMesh。

editors/mesh

069 编辑模式里的修改器笼子是什么功能？

求值出 cage / final 两份：BKE_object_get_editmesh_eval_cage 与 _final。你可以在变形后的表面上选点，工具仍写回基 BMesh。

看起来「点在细分后的位置」，数据还在未 Apply 的基网格上。

editbmesh_calc_modifiers · 修改器

070 对称编辑（X 镜像）是修改器吗？

通常是编辑工具在 BMesh 上对对称元素同步，或 Mesh 上的对称选项。和 Mirror 修改器叠加时，用户容易混：一个改基网格，一个求值时复制。

先分清「破坏性对称」还是「栈上镜像」。

BMO · modifiers

071 法线重算是独立功能还是更新的副作用？

两者都有。工具可调专门 Operator；EDBM_update 也会按参数重算法线 / looptris，供编辑绘制。用户不点「重算法线」，挤出后看起来仍正确，是因为更新带了这一步。

这不是 depsgraph 修改器栈。

BKE_editmesh_looptris_and_normals_calc · 更新

072 合并（M）与溶解有何功能差别？

合并把多个顶点焊到一点；溶解去掉元素并尽量保持周围面。都是 BMesh 拓扑工具，不是修改器。结果立刻在编辑态可见，退出才写回数组。

功能名接近，BMO 入口不同。

editors/mesh

073 选择模式（点/边/面）存在哪？

编辑网格的 selectmode 跟着 BMEditMesh / 工具设置。它改的是后续 Operator 解释选择的方式，不是换数据块。transform 和 BMO 槽 verts=%hv 按当前选择填充。

物体模式没有这三档。

EDBM_op_callf · BMO 槽位

074 隐藏顶点（H）影响渲染吗？

编辑隐藏主要影响编辑态显示与选择。F12 用的是求值网格；未退出时会经 wrapper 转换。不要默认「H 掉的面 F12 一定没有」——要看是否写回、是否有修改器重建。

物体级 hide-render 才是渲染图的硬开关。

编辑模式 · 可见性

075 撤销挤出撤销的是 BMesh 还是修改器结果？

带 OPTYPE_UNDO 的网格 Operator 结束时 ED_undo_push_op。撤销恢复的是数据块（含编辑态），不是单独把 EEVEE 帧回退。修改器预览会随基网格重求值。

Python bpy.ops 默认常压住 undo，除非 is_undo。

OPTYPE_UNDO · 撤销

076 为什么「看起来光滑」有时只是着色，不是拓扑功能？

Auto Smooth / 平滑着色写的是法线与标志，面数不变。细分修改器才加拓扑。功能上都叫光滑，模块不同：一个常是 Mesh 标志 + 绘制，一个是 modifiers + 求值。

看边数有没有涨，就能分开。

Mesh · modifiers

修改器与 Apply

077 添加细分修改器时为什么网格没有立刻变密？

点添加只往 Object.modifiers 塞 ModifierData。变形在下一轮 depsgraph：BKE_object_eval_uber_data。视口看到的是求值副本。

基网格顶点数可以不变。这是非破坏功能的核心。

Object.modifiers · 栈在物体上

078 视口细分级别和渲染级别为什么能不同？

同一 mesh_calc_modifiers，模式是 eModifierMode_Realtime 还是 Render，再读修改器上的视口/渲染级别。视口图与 F12 图因此分叉。

功能上为了交互帧率；不要以为 F12「少算了一级」是 bug。

eModifierMode_Realtime · modifier-eval

079 Apply 修改器是什么功能，编辑模式为何不能 Apply？

OBJECT_OT_modifier_apply 把当前求值结果烤进原始 Mesh（BKE_mesh_nomain_to_mesh）并删除该修改器。编辑模式真相在 BMesh，不允许这条破坏路径。

Apply 之后文件里的基网格变了；未 Apply 的求值结果不进文件。

object_modifier.cc · Apply 不是求值

080 禁用修改口视口显示，F12 还会算它吗？

可以。Realtime 与 Render 开关独立。视口关掉、渲染打开是常见档。两张 depsgraph 分别尊重 hide 与模式标志。

功能测试：只看视口不能断定 F12 网格。

DAG_EVAL_RENDER

081 修改器顺序是功能还是实现细节？

是功能。链表顺序就是栈顺序，mesh_calc_modifiers 按序 BKE_modifier_modify_mesh。先镜像后细分与相反，结果不同。

面板上的上下箭头改的是 DNA 链表，不是「显示排序」。

BKE_modifier_modify_mesh · modifiers

082 几何节点修改器能代替编辑模式吗？

不能代替。节点在求值时把网格当数据处理；挤出、点选、溶解仍是 BMesh 工具。节点可以生成新几何，但那是修改器输出，不是 edit_mesh。

想对节点结果用编辑工具，通常要 Apply 或用其它工作流把几何变成可编辑 Mesh。

modify_geometry_set · geometry / 节点

083 约束（constraint）和修改器是同一功能吗？

都在求值时作用，但约束主要改变换，修改器主要改几何。用户都觉得「叠效果」。本站深讲修改器；约束点到 depsgraph TRANSFORM 即可。

不要在 modifiers/ 里找 Copy Rotation。

depsgraph

084 形态键是修改器功能吗？

形态键存在 Mesh 上，求值时混进几何，常和修改器栈协同。它不是 ModifierTypeInfo 表里的一种类型（有独立数据）。功能上像非破坏变形。

编辑形态键仍可能进编辑模式改对应坐标。

blenkernel

085 为什么移动修改器参数视口会刷新，却没有「运行修改器 Operator」？

拖参数是 RNA 属性链：写 DNA → prop->update → DEG_id_tag_update。下一圈 depsgraph 重跑 modify_mesh。没有单独的「执行修改器」命令。

这和挤出必须跑 Operator 正好相反。

RNA_property_update · UI–数据问答

086 实例化（collection instance）算修改器吗？

不算。实例在 depsgraph 展开，Draw/Cycles 看到多个物体。源网格仍一份。功能上「场景里很多」，数据上可能只有一块 Mesh。

和 Array 修改器结果相似、机制不同：Array 常真正生成几何。

depsgraph

087 编辑模式启用修改器（On Cage / Edit Mode）是什么功能开关？

部分修改器声明可在编辑模式运行。求值走 editbmesh_calc_modifiers。关掉则编辑态只看基 BMesh，物体模式/渲染仍可套栈。

不是所有修改器都支持编辑态。

modifierType_Subsurf · 注册

088 「把修改器应用到形态 / 作为形态键」为何另有 Operator？

普通 Apply 替换基网格。应用到形态键要写 shape 数据，仍是 object 编辑器命令，不是修改器 modify_mesh 自己决定「写回哪里」。

功能入口在面板按钮，计算仍先求值再烤。

OBJECT_OT_modifier_apply · editors/object

材质、视口、F12

089 给物体换材质，改的是网格还是物体？

槽位在 Object 或 Mesh 的 Material **mat（DNA）。节点树是独立 ID。换材质不改拓扑，标 SHADING / 相关 recalc，Draw 或 Cycles 重编着色。

功能上「看起来换了皮」，模块上是 ID 引用。

Material · shader nodes

090 节点里加 Principled，视口为何有时没变？

Solid/Workbench 不走完整节点 GPU 材质。要 Material 或 Rendered 且引擎吃 EEVEE 编译。功能上用户已「做了材质」，显示模式过滤了结果。

F12 用 Cycles 时走另一套 add_nodes，和当前着色模式无关。

Workbench · GPU 材质

091 视口着色切换（Z）会重算修改器吗？

通常不。它改 View3D shading.type，Draw 换引擎组合。几何求值已经在 WM 刷新里做过。换 Solid ↔ Material 不应重建 BMesh。

若场景被标脏，刷新是另一回事，不是 Z 本身的功能。

ED_view3d_engine_type · 一帧

092 线框模式是引擎还是叠加？

着色模式线框走 Workbench；编辑边、线框叠加还可能是 overlay。功能上都叫线框。看是「整个场景用线框引擎」还是「实体上再描边」。

谁上、谁叠

093 按 F12 会不会走当前视口那条像素管线？

不会共享像素后端。F12：RENDER_OT_render → 渲染 depsgraph（DAG_EVAL_RENDER）→ RE_engine_render。视口继续 Draw。共享的是求值语义，不是 framebuffer。

引擎字符串决定 Cycles 还是 EEVEE 出图。

scene.r.engine · F12 · 渲染地图

094 视口渲染（Viewport Render）和 F12 有何功能差别？

视口渲染常按当前 View3D 引擎/相机抓一帧，更接近「把视口变成图」。F12 走 render 作业、图层、分辨率、Render 修改器级别。都可能叫 EEVEE，图不同。

按钮在 editors/render，不要当成第二次 DRW_draw_view 那么简单，但也不要当成 Cycles kernel。

editors/render

095 场景引擎设为 Cycles 时，材质球为何仍像 EEVEE？

许多预览走 RE_USE_EEVEE_VIEWPORT：用 EEVEE 编译节点做球预览。功能上预览「够快」，不是 bug。真正 F12 才 BlenderSync + kernel。

对照节点在 Cycles 独有闭包上的差异，不要只看材质球。

RE_USE_EEVEE_VIEWPORT · Draw

096 动画播放时修改器每帧都算吗？

换帧走 DEG_evaluate_on_framechange。依赖时间的修改器/节点会重算；没标脏且无时间依赖的可以复用缓存。功能上「播起来网格在动」，实现上是求值图按关系更新。

不是每一帧都从 BMesh 重建。

DEG_evaluate_on_framechange · Depsgraph

097 保存文件会保存修改器预览网格吗？

默认保存 DNA：基 Mesh + 修改器参数。求值副本、GPU 网格批、Cycles BVH 不进 .blend。下次打开再求值。

Apply 过的才变成基网格的一部分。

blenloader · makesdna

098 用户按 Ctrl+Z 和按 F12 在功能上如何衔接？

撤销恢复 Main 里的 ID。下一次刷新 depsgraph 用新数据求值；若正在渲染，作业看到的是渲染图上的求值世界。两条功能不要合成一个「系统撤销渲染器」。

渲染中途撤销是产品行为，分析时记住数据源是 ID，不是 tile 缓冲。

撤销 · render

099 「同一套节点、两套样子」是功能缺陷吗？

是设计。节点语义共享，编译器分叉：光栅近似 vs 路径追踪闭包。功能上允许视口快、F12 准。差异大时查的是两套编译，不是 DNA 存了两份树。

d-shaders.svg · 节点 → 闭包

100 这 50 个功能题故意不写什么？

雕刻笔刷、UV 岛、权重绘制、合成节点、序列、导入导出格式。它们会穿过别的 editors。网格编辑 + 修改器 + 视口/F12 已经够把主线走完。
