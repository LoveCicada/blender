4.1 depsgraph 与求值副本

2.3 的标脏只是「打标志」。这课看标志之后谁干活：depsgraph 在事件循环空档求值，并且原始 ID 不动——修改器、驱动、矩阵全写在求值副本上。

路径索引 3.5 修改器 4.1 求值副本 4.2 两张图

目标

  • 说出标脏之后：谁在什么时候、按什么顺序重算。
  • 说出求值副本（copy-on-eval）是什么，用 evaluated_get 拿到它。
  • 用实验证明：改原始物体，副本不立刻变，求值后才跟上。

概念：图、空档、副本

depsgraph 把「谁依赖谁」编成一张图：物体变换 → 修改器 → 约束 → 驱动……2.3 的 DEG_id_tag_update 在图上标脏若干节点。真正的重算发生在事件循环的空档：Blender 一圈事件处理完，发现图脏了，才按依赖顺序重算脏节点——这就是「改了数据 ≠ 立刻重算」的完整答案。

重算时不碰原始 ID。每个需要求值的 ID 得到一份求值副本（5.x 源码里叫 copy-on-eval）：修改器输出、驱动结果、最终矩阵都写在副本上。原始 ID 保持「文件里的样子」，副本是「此刻算出来的样子」。视口画的是副本，渲染用的也是副本（3.5 已经见过顶点数差异）。

1.1 里 ID 头的 recalc 标志，就是这套机制留在数据块上的脸。

源码走读：入口与副本

  • 对外求值入口 DEG_evaluate_on_refresh：声明 depsgraph/DEG_depsgraph.hh:201，实现 depsgraph/intern/depsgraph_eval.cc:55。
  • 谁调它：blenkernel/intern/scene.cc:2798 的 scene_graph_update_tagged，:2829 调用；换帧走 DEG_evaluate_on_framechange（:2916）。
  • 副本机制：depsgraph/intern/eval/deg_eval_copy_on_write.h:53 的 deg_create_eval_copy——求值节点开工前先把原始 ID 复制成求值副本。
  • 取副本：C 侧 DEG_get_evaluated_id（depsgraph_query.cc:238）；bpy 侧 ID.evaluated_get（RNA 登记在 rna_ID.cc:2611）。

动手实验：副本何时跟上

控制台逐段执行：

import bpy
ob = bpy.context.object
dg = bpy.context.evaluated_depsgraph_get()
ev = ob.evaluated_get(dg)
ob.is_evaluated, ev.is_evaluated
# 预期：(False, True) —— 原始与副本，一眼可辨
ob.location.x = 7.0
ev.location.x
# 预期：还是旧值 —— 标脏已打，但求值没跑，副本没跟上

bpy.context.view_layer.update()      # 强制结算一次
dg2 = bpy.context.evaluated_depsgraph_get()
ob.evaluated_get(dg2).location.x
# 预期：7.0 —— 求值后副本跟上（旧 dg / ev 已失效，要重新拿）

这段实验把 2.3 的「空档才重算」落到了可观察的指针上：ev 是旧求值周期的快照，新周期要重新取图、重新取副本。
