6.1 几何节点：修改器里的程序

几何节点不是新模块、不是 BMesh 替代——它是一个修改器：求值时把几何当数据过一遍节点树，输出新几何。节点树里流的也不是固定值，而是字段（field）：到用的地方才按上下文取值的「延迟函数」。

路径索引 6.1 几何节点 6.2 合成 6.3 雕刻 6.4 UV 6.5 权重 6.6 约束 6.7 EEVEE 探针

目标

  • 说出几何节点在架构里的位置：修改器的一种，跑在 depsgraph 求值时。
  • 解释「字段」和「直接值」的区别。
  • 用 bpy 从零建一个能出结果的几何节点修改器。

概念：修改器 + 字段

两个概念撑起整个专题：

  • 它是修改器：面板里「添加几何节点」就是加了一个 NodesModifierData，类型 Constructive（建设性——可以生成全新几何）。求值时机、标脏、Apply 语义全部沿用阶段 3 的修改器链，没有第二条路。
  • 字段（field）：节点之间连的菱形接口流的是字段——不是「一个数」，而是「给我一个上下文（比如某个顶点的位置），我算出对应的值」。位置、编号、法向都是内置字段。圆接口流的才是算好的具体数据（几何、数值）。

所以节点图不是「从左到右算一遍」的脚本，而是一张求值计划：字段在被消费的那一刻，按消费方给的上下文批量求值。这也是它能高效处理百万顶点的原因。

源码走读：修改器壳与字段核

  • 修改器注册：MOD_nodes.cc:2171 的 modifierType_Nodes，数据块 NodesModifierData（:2174），类型 Constructive。
  • 求值入口：MOD_nodes.cc:1862 的 modify_geometry_set——吃进 GeometrySet，跑节点树，吐新 GeometrySet；:2191 把它挂进 ModifierTypeInfo。
  • 字段抽象：source/blender/functions/FN_field.hh:45 的 template<typename T> class Field；批量求值器 FieldEvaluator 在 FN_field_evaluation.hh:21。
  • 节点实现：source/blender/nodes/geometry/nodes/ 一节点一文件，比如立方体 node_geo_mesh_primitive_cube.cc。
  • 底层算法库 source/blender/geometry/ 是无状态的——节点树由修改器驱动它，不是反过来（见自检 Q015）。

动手实验：bpy 建一个「立方体生成器」

官方二进制控制台逐段执行（先选中一个物体，比如默认 Cube）：

import bpy
ob = bpy.context.active_object
mod = ob.modifiers.new("GeoDemo", 'NODES')
mod.bl_rna.properties["node_group"]
# 预期：指针属性 —— 修改器只存「指向节点组」的引用
ng = bpy.data.node_groups.new("GeoDemoTree", 'GeometryNodeTree')
ng.interface.new_socket("Geometry", in_out='INPUT', socket_type='NodeSocketGeometry')
ng.interface.new_socket("Geometry", in_out='OUTPUT', socket_type='NodeSocketGeometry')
mod.node_group = ng
# 预期：修改器面板出现空节点组 —— 5.x 用 interface 声明组输入输出
n_in = ng.nodes.new("NodeGroupInput")
n_out = ng.nodes.new("NodeGroupOutput")
cube = ng.nodes.new("GeometryNodeMeshCube")
n_in.location = (-300, 0); cube.location = (0, 0); n_out.location = (200, 0)
ng.links.new(cube.outputs["Mesh"], n_out.inputs["Geometry"])
# 预期：视口里原物体被替换成节点生成的立方体 —— 原 Mesh 没动

验证「原数据没动」：删掉修改器（ob.modifiers.remove(mod)），原物体原样回来。这就是 Q018 说的「是修改器，不是 BMesh 替代」——想永久改拓扑，只能 Apply。
